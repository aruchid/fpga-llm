# FPGA 大模型推理项目：设计思路与验证

讲清楚三件事：这个项目整体是怎么考虑的，做了哪些测试，每类测试证明了什么、没证明什么。具体数字见 [FPGA 大模型推理项目进度报告](00-进度报告.md)，各部分设计细节见文末链接。

---

## 一、项目要回答的问题

最终目标是：一块 FPGA 加速卡通过 PCIe 插在电脑上，跑一个大模型的推理（逐个生成 token）。

但在买板子、上板调试之前，有几个问题必须先回答。否则可能买错板、白写一大堆硬件：

1. **算法能不能用整数硬件实现，精度会掉多少？** FPGA 上没有方便的浮点，要换成 int8 / 定点数。
2. **硬件逻辑写得对不对？** RTL 里任何一个位宽、对齐、舍入的错误，都可能让模型输出乱码，而且很难在板上调。
3. **能跑多快？瓶颈在哪？** 该买什么板（带宽、容量、PCIe），硬件做多大并行度。
4. **硬件能不能真的综合出来、跑到多高频率、占多少资源？**

所以这一阶段的定位是：**不碰板子，只用仿真和估算，把整个模型从算法到硬件的问题都搞清楚**。

---

## 二、整体思路

### 1. 分层：每一层都有上一层当"标准答案"

| 层 | 是什么 | 回答哪个问题 | 它的"标准答案" |
|---|---|---|---|
| L0 浮点版 | 普通 numpy 浮点推理 | 模型本身对不对 | 能生成通顺故事（与 llama2.c 同一份权重） |
| L0 硬件等价版 | 只用整数运算，每一步都和硬件打算做的一样 | 问题 1：精度 | L0 浮点版 |
| L1 性能模型 | 用公式算周期、字节数、耗时 | 问题 3：速度与选板 | 周期公式由 L2 RTL 实测校准 |
| L2 RTL | SystemVerilog 硬件 + 仿真 | 问题 2：硬件对不对 | L0 硬件等价版（逐比特） |
| 综合 / 时序 | yosys 综合 + 自写时序估算 | 问题 4 | 暂无（等 Vivado） |
| L3 上板 | 未开始 | 真实带宽、真实频率 | L2 + L1 |

**为什么这样分**：如果直接写 RTL 然后和浮点模型比，出了偏差分不清是"定点化本来就有的误差"还是"硬件写错了"。中间插一个**整数的硬件等价版**后，两类问题彻底分开：

- 浮点 vs 硬件等价版：只有**量化误差**，用统计指标衡量（一致率、余弦相似度），允许有差距。
- 硬件等价版 vs RTL：两边都是整数、同一套舍入规则，**必须一个比特都不差**。任何不一致都是 bug，不存在"误差在容忍范围内"把 bug 藏起来的可能。

这是整个项目最核心的一条原则：**RTL 的正确性标准是逐比特一致，不是"差不多"。**

### 2. 选 stories15M 当验证模型

- llama2.c 格式的小 Llama（dim 288、6 层、6 头、FFN 768、词表 32000、最长 256），**结构和真正的 Llama 一样**：RMSNorm、RoPE、SwiGLU、KV Cache、共享输出层。
- 足够小，**整个模型能在 RTL 仿真里跑完**（每 token 约 55 万周期，仿真几分钟出一个 token）。大模型只能抽几次矩阵乘验证，小模型可以端到端验证。
- 在它上面验证过的硬件，换大模型只是尺寸参数不同（L1 用同一套公式外推到 110M、1B、7B）。

### 3. 数值格式的取舍

| 数据 | 格式 | 理由 |
|---|---|---|
| 权重 | int8 + 每行一个缩放系数（Q24） | 解码时每个 token 要把全部权重读一遍，**权重字节数直接决定速度上限**，压到 8 位最划算 |
| 激活 | Q16.16 定点（int32） | 非线性运算需要精度和范围；32 位在模型实测范围内不溢出 |
| 进矩阵乘前的激活 | int8 + 2 的幂移位（每个向量一个） | 移位代替乘法，硬件最省；每向量动态选移位量保留精度 |
| KV Cache | int8 + 每头一个移位 | 长上下文时 KV 读取量随长度增长，同样要省带宽 |
| 1/√x、1/x、exp、sigmoid、RoPE | 查表 + 插值 / 牛顿迭代 | FPGA 上做这些函数的标准做法，详见 [FPGA 上的非线性算子](02-非线性算子原理.md) |

所有位宽都用**真实模型的实测数值范围**确认过（矩阵乘累加 18~19 位，×缩放 32~34 位，P·V 35 位），并写成 RTL 的输入约定。

### 4. "运算流"：一份描述，三处使用

一次前向计算被拆成 7 种运算组成的序列：`rmsnorm、quant、matmul、rope、attn、silu_gate、resadd`。这份序列只写一次（`HWModel.forward_steps`），然后：

- L0 按它在 Python 里执行；
- L1 按它统计运算量和周期；
- L2 调度器按它把每个运算交给 RTL 执行。

这样保证三者**做的是同一组运算**，不会出现"性能模型漏算了某一步""RTL 少实现了某个运算"。测试里也专门检查了 L1 的统计和 L0 实际执行逐项相等。

### 5. 先求对，再求快，最后求能综合

- 第一版 RTL 只求正确：内部 128 位、组合逻辑一拍算完，先和 L0 逐比特对上。
- 然后把整模型跑通（调度器 + 全部向量单元）。
- 最后再改成可综合：限定位宽、改块 RAM、插流水线。**每改一步都重跑全部测试**，所以优化过程中引入的错误能立刻发现。

有了逐比特一致这条硬标准，激进地改流水线才是安全的。

### 6. 性能模型的定位

L1 不是拍脑袋的估算：**凡是能用仿真测的都测了再写进公式**（矩阵单元、每种向量运算的周期），只有板卡带宽、PCIe 延迟、驱动开销这类必须上板才能测的量用公开规格假设，并标明"未验证"。它的作用是**在花钱前做决定**：选什么板、做多大并行度、要不要做 GEMM、要不要把非线性也搬上 FPGA。

## 三、测试清单

全部自动化测试一条命令跑完（`pytest`），共 **36 项**，全部通过。其中 3 项是 RTL 仿真的入口，每项内部再跑若干个 cocotb 仿真测试（共 13 个）。另有几项耗时长的"大测试"用环境变量手动开启。

### A. L0 定点算子：精度测试（`tests/test_fixedpoint.py`，22 项）

每个定点函数和数学上的精确值比，检查误差在设计预期内。

| 测试 | 做法 | 通过标准 |
|---|---|---|
| rshift_round | 正负数、奇偶、负移位（变左移） | 舍入方向完全符合规定 |
| rsqrt（8 个值，1e-4 到 12345） | 与 1/√x 比 | 相对误差 < 2×10⁻⁴ |
| recip（6 个值，1 到 1e5） | 与 1/x 比 | 相对误差 < 10⁻⁴ |
| exp2 | −20 到 0 共 2001 个点 | 绝对误差 < 5×10⁻⁵ |
| softmax | 20 组随机长度、随机幅度 | 误差 < 2×10⁻⁴，和为 1（±0.005） |
| sigmoid / silu | −12 到 12 共 4001 点 | 误差 < 2×10⁻³ |
| rmsnorm | 幅度 0.05 / 1 / 30 | 相对误差 < 2% |
| quantize_shift | 幅度 10⁻³ 到 5000 | 结果在 ±127 内；移位量是最小的（不浪费精度）；还原误差 ≤ 1 个量化步长 |
| int_matmul | 随机矩阵 × 向量 | 相对误差 < 2% |
| rope | 3 个位置 | 误差 < 10⁻³ |

**意义**：每个积木单独是准的，误差来源清楚。如果整模型精度不行，可以定位到具体哪个算子。

### B. L0 整模型（`tests/test_model.py`，4 项）

| 测试 | 证明什么 |
|---|---|
| weights_roundtrip | llama2.c 权重格式读写无损（共享 / 不共享输出层两种） |
| hw_tracks_float | 随机权重小模型：硬件等价版与浮点版逐位置比较，平均余弦相似度 > 0.995、最低 > 0.98、下一个词一致率 > 85% |
| hw_is_deterministic | 硬件等价版两次运行结果完全相同（RTL 比对的前提：标准答案本身必须是确定的） |
| tokenizer | 分词与还原，含词表外字符的字节回退 |

另外在**真实 stories15M** 上手动做过精度评估（`l0/run.py`）：

- 生成 64 个 token，前 44 个与浮点版完全相同，之后分叉，两边都是通顺的故事；
- 同一输入逐位置比较：下一个词一致率 96.9%，logits 余弦相似度平均 0.9991、最低 0.980。

**意义**：回答问题 1——int8 权重 + 定点激活**对这个模型够用**，精度损失很小。这决定了整个硬件方案可行。

### C. L1 性能模型（`tests/test_l1.py`，6 项）

| 测试 | 证明什么 |
|---|---|
| mvm_cycles_match_rtl | 矩阵单元周期公式与 RTL 实测**完全相等**：第一版 RTL（2917、7777、7237、324001，整 token 530,737）和当前版（2683、7078、7003，整 token 483,564）两套都对 |
| inventory_matches_l0（2 个位置） | L1 统计的每种运算元素数、MAC 数与 L0 实际执行逐项相等 |
| weight_bytes_match_packed_stream | L1 算的每 token 读权重字节数与实际权重量相符（15.39 MB，误差 1% 内） |
| decode_sane | 耗时的合理性：每 token 在 0~10 ms 之间；只放矩阵乘（A0-MMIO）比整模型上 FPGA（A1）慢；并行度加大不会变慢 |
| vpu_cycles_match_rtl | 6 种向量运算的周期公式与 RTL 实测平均值相等（两版 RTL 都写在测试里） |

**意义**：L1 里能验证的部分都锁死在测试里。以后改了 RTL，周期变了，这个测试会失败，提醒同步更新性能模型。这样 L1 给出的选板结论才可信。

### D. L2 矩阵单元 RTL（`l2/tb_mvm.py`，5 个仿真测试）

| 测试 | 做法 | 证明什么 |
|---|---|---|
| id_register | 读 ID、状态寄存器 | AXI-Lite 总线通 |
| random_shapes | 6 种尺寸（含 1×7、40×50 这种不是 32 倍数的，K 最大 1024）+ 移位量边界（0、1、24、25） | 尾块处理、移位左右方向切换都对 |
| saturation | 全 ±127 权重 + 最大缩放系数 | 超出 int32 时饱和而不是回绕 |
| backpressure | 权重流 30% 概率断流，结果流 50% 概率不收 | 握手逻辑在任意停顿下不丢数、不重复、结果不变 |
| stories15m_replay | 截取 L0 在真实模型上的矩阵乘调用（默认 7 次，`L2_FULL=1` 时一个 token 全部 43 次）原样送进 RTL | 真实数据分布下逐比特一致，并测出真实周期 |

全部是**与 L0 逐比特比对**。

### E. L2 向量单元 RTL（`l2/tb_vpu.py`，7 个仿真测试）

| 测试 | 覆盖的情况 |
|---|---|
| quantize_shift | 正常范围、int32 满幅、全零、恰好 127/128 边界、超过 32 位（RoPE 之后可能出现）、单元素 |
| rmsnorm | 长度 7~768，幅度 0.001~300，**全零输入**（除零保护） |
| softmax | 长度 1~256，幅度很大的输入、−1000 这种极小值（指数下溢为 0） |
| elementwise | 残差相加（含饱和）、SiLU 门控（正常 + int32 满幅大数） |
| rope | 头维度 16/48/64，位置 0~1000，int32 满幅输入 |
| attention_head | 头维度 16/48/64，上下文长度 1~100，随机 int8 的 q/K/V 和随机移位量 |
| cycle_profile | 各运算在多种尺寸下的周期，用来拟合 L1 公式 |

**意义**：每种非线性运算的硬件在**边界值**上也和参考模型一致。边界值（全零、满幅、单元素、极端指数）正是硬件最容易出错的地方。

### F. 整模型 RTL 推理（`l2/tb_sched.py`）

电脑端调度器按运算流，把每个运算交给 RTL 执行（矩阵乘给矩阵单元，其余给向量单元），只有词嵌入查表和最后取最大值在电脑端。每生成一步都把 RTL 算出的 32000 个 logits 和 L0 比较。

| 运行方式 | 内容 | 结果 |
|---|---|---|
| 默认（自动测试里） | 随机权重小模型，生成 8 步 | 每步 logits 逐比特一致 |
| `L2_GEN_MODEL=stories15M`（手动） | 真实模型，提示词 "Once upon a time"，生成 32 步 | 每步逐比特一致，输出 "Once upon a time, there was a little girl named Lily. She loved to play outside in the sunshine. One day, she saw a big…" |

另有开关可以只让矩阵乘走 RTL（`L2_GEN_VPU=0`），或不合并共用输入的矩阵乘（`L2_GEN_FUSE=0`），用来定位问题。

**意义**：这是最强的一项证据——**整个模型的全部运算在硬件逻辑上跑，结果和参考模型一个比特都不差**。单元测试证明每块积木对；这个测试证明积木之间的接口、数据格式、调度顺序、KV Cache 读写都对。同时测出了真实的每 token 周期（546,765）。

### G. 打包格式（`l2/test_l2.py::test_pack_layout`）

检查电脑端把权重、输入打包成硬件数据流的格式（每个 tile 先 4 拍缩放系数、再 kb×32 拍权重），以及解包结果。软件和硬件对数据排布的理解一致，是上板后 DMA 能用的前提。

### H. 综合与时序（非自动测试）

- yosys `synth_xilinx` 综合全部单元：**能综合**，得到资源数（约 14,800 LUT、118 DSP）。
- 自写的 `synth/sta_est.py` 找最长寄存器到寄存器路径并标出源码信号，据此逐个切流水线：最慢单元从 20 MHz 提到约 115 MHz（7 系列粗估）。
- Verilator 以 `-Wall` 编译无警告（位宽不匹配这类问题在编译时就会暴露）。

**意义**：回答问题 4 的大方向——设计放得进 Artix-7 级别的芯片，频率在百 MHz 量级。但这是粗估，见下文"没有覆盖的部分"。

## 四、测试真正抓到过的问题

测试不是摆设，开发过程中它们实际拦下了这些 bug：

| 问题 | 怎么发现的 | 如果没发现会怎样 |
|---|---|---|
| 矩阵单元第一版乘法在 8 位里做，乘积溢出 | random_shapes 不一致 | 矩阵乘结果全错 |
| 指数流水线延迟数错一拍 | 向量单元比对不一致 | softmax 和注意力结果错位 |
| SiLU 门控里 x 和 sigmoid 错开一拍相乘 | elementwise 不一致 | FFN 输出错，模型乱码 |
| quant 输出 FIFO 太浅，每 7 拍停 1 拍 | cycle_profile 周期与公式对不上 | 结果对但慢 17%，性能模型会偏乐观 |
| 若干位宽截断、符号扩展问题 | 边界值用例 + Verilator 警告 | 只在特定数值下出错，上板极难查 |

其中 quant 那个最能说明 L1 与 RTL 互相校验的价值：**结果完全正确的 bug**，只有周期对不上才能发现。

## 五、这些测试没有覆盖的部分

要诚实看待：仿真通过不等于上板就能跑。目前**没有**验证的：

| 没覆盖 | 风险 | 计划 |
|---|---|---|
| 真实时序 | 粗估可能偏乐观或偏保守，布线延迟没算 | Vivado 综合 + 布局布线 + 时序报告 |
| 真实 DDR、PCIe | L1 里带宽、延迟是假设值；仿真里权重是直接送进去的 | 上板实测；写从 DDR 读权重的 DMA |
| 长上下文 | 整模型只跑到 32 步左右；注意力单元测到长度 100，满长度 256 未在整模型中跑 | 可补一次满长度整模型仿真（耗时长） |
| 片上调度 | 现在由电脑逐个运算下发，每 token 要与电脑往返很多次 | 写片上调度器 |
| 多时钟域、复位中途、异常输入 | 测试都在单时钟、正常复位下进行 | 上板集成时补 |
| 覆盖率 | 没有统计代码 / 状态覆盖率，没做形式验证 | 视需要补 |
| 预填充 | 只实现了逐 token 的矩阵 × 向量，没有 GEMM | L1 已估出收益，后续设计 |
| 更大的模型 | 只在 stories15M 上端到端验证；更大模型是 L1 外推 | 选板后用 110M 再验一次 |

还有两点已知的简化：独立的 softmax 单元只用于测试（注意力头内部自带 softmax）；词嵌入和取最大值在电脑端。

## 六、总结：现在能确定什么

1. **算法可行**：int8 权重 + 定点激活，在 stories15M 上精度损失很小（一致率 96.9%）。
2. **硬件逻辑正确**：整个模型的全部运算在 RTL 上执行，32 步生成与参考模型逐比特一致；每个单元在边界值上也一致。
3. **性能心里有数**：每 token 约 55 万周期；解码速度由存储带宽决定，并行度要与带宽匹配，片外容量决定能跑多大的模型；整模型上 FPGA 后 PCIe 开销可以忽略。
4. **能综合**：资源约 Artix-7 200T 的 11% LUT、16% DSP，粗估约 115 MHz。

还不能确定的：真实频率、真实带宽、上板后的整体集成。这些是下一阶段（Vivado 时序 → 片上调度器 → DDR DMA → 选板上板）要回答的。
