# 测试报告：原始推理 vs 32×32 矩阵推理

**被测对象**：SD-Turbo 文生图（512×512，4 步）
**对比项**：diffusers + cuDNN 的原始推理 / 把全部矩阵乘换成 32×32 int8 矩阵单元的实现
**结论先行**：矩阵替换覆盖 **99.1%** 的算力，画质 PSNR **22.00 dB**、逐像素可复现，
但**耗时从 0.94 s 变成 3.17 s（慢 3.4 倍）**。慢的原因不是 int8 或 32×32 分块，
而是**没有做算子融合**：多出来的访存与 kernel 启动吃掉了 int8 省下的算术时间。

## 2. 被测模型

| 组件 | 参数量 | 作用 | 输入 → 输出 |
|---|---|---|---|
| CLIP 文本编码器（OpenCLIP ViT-H/14） | 354.0 M | 提示词编码 | 77 token → 77×1024 |
| UNet（4 down / mid / 4 up） | 865.9 M | 4 步去噪 | 64×64×4 → 64×64×4 |
| VAE 解码器（AutoencoderKL） | 83.7 M | latent → 像素 | 64×64×4 → 512×512×3 |

### 算力构成（实测统计）

| 阶段 | MACs | 占比 | 每张图执行 |
|---|---|---|---|
| CLIP | 23.5 GMAC | 0.9% | 1 次 |
| UNet | 1356.4 GMAC | 51.8% | 4 次（339.1 GMAC/步） |
| VAE | 1240.1 GMAC | 47.3% | 1 次 |
| **合计** | **2619.9 GMAC** | 100% | |

两个反直觉的事实：

1. **VAE 与 UNet 算力几乎相等**：VAE 只有 84 M 参数，但它在 512² 上卷积，像素数是 UNet 的 64 倍。
2. **文本编码只占 0.9%**：它是否量化对整体几乎没有影响。

## 3. 原始推理（基线）：cuDNN 怎么算

### 3.1 链路

```
提示词 → CLIP 编码(context 77×1024) → 初始噪声
      → UNet × 4 步（每步：eps = UNet(x, t, ctx)，x ← Euler 更新）
      → VAE 解码 → 512×512×3
```

### 3.2 各阶段实测

| 阶段 | 时间 | 吞吐 |
|---|---|---|
| CLIP | 0.02 s | 1.2 TMAC/s |
| UNet × 4 | 0.47 s | 2.9 TMAC/s |
| VAE 解码 | 0.26 s | 4.8 TMAC/s |
| **合计** | **0.94 s（fp32）/ 0.80 s（fp16）** | 2.8 TMAC/s |

cuDNN 的每一个卷积都是**一个融合 kernel**：读输入 → 隐式 im2col → 乘加 → 写输出，中间结果从不落到显存。
另外 3×3 卷积会走 **Winograd 变换**，把乘加数量降到约 2.25 分之一。

---

## 4. 我们的推理：32×32 int8 矩阵单元怎么算

### 4.1 替换范围

遍历 UNet 与 VAE 的模块树，把 **101 个 Conv2d** 和 **220 个 Linear** 全部替换成量化版本：

| 组件 | 卷积 | 线性层 | 是否替换 |
|---|---|---|---|
| UNet | 66 | 216 | 全部 |
| VAE 解码器 | 35 | 4 | 全部 |
| CLIP | — | — | **未替换**（保持浮点） |

### 4.2 单个卷积层内部（8 步）

```
1 布局转换     (N,C,H,W) → (H,W,C)
2 补边        zeros + 切片拷贝
3 按像素分块   每块 8192 个输出像素
4 im2col      9 次切片拼成 (8192, 9C) 矩阵
5 量化        每行求 max → scale = max/127 → round → int8
6 矩阵乘      int8 (O,9C) × int8 (9C,8192)ᵀ → int32
7 反量化      y = acc × (s_w × s_a) + bias
8 写回        (Hout,Wout,O) → (N,O,Hout,Wout)
```

权重的 scale 在加载时算一次（per 输出通道）；**激活的 scale 在运行时每个像素现算**（动态量化）。

### 4.3 32×32 矩阵引擎

第 6 步的 GEMM 按硬件的方式切块：

```
nt = ⌈M/32⌉  输出 tile 数（32 行一个 tile）
kb = ⌈K/32⌉  K 方向块数（32 元素一块）
周期 = B · nt · (kb·32 + 4)      每拍一行权重（32 个 int8）
```

以 320→320、3×3、64×64 输入的一层为例：

| 项 | 值 |
|---|---|
| M / K / B | 320 / 2880 / 4096 |
| tile 数 | 10 × 90 × 128 = **115,200** |
| MACs | 3.77 GMAC |
| 硬件周期 | 118 M 拍 ≈ **1.03 s @115 MHz** |

引擎有两种累加模式（**输出逐比特相同**）：

| 模式 | 做法 | 全链耗时 |
|---|---|---|
| 快速（默认） | 整段 K 一次 IMMA | 2.94–3.17 s |
| `--strict-tiles` | 每 32 元素块一次 IMMA + int32 相加 | 8.9 s |

### 4.4 量化方案

| 部分 | 方案 |
|---|---|
| 权重 | per-channel int8（每输出通道一个 scale） |
| 激活 | per-row int8（每像素 / token 一个 scale） |
| 矩阵乘 | int8 × int8 → int32（IMMA），32×32 分块 |
| 反量化 | `acc × s_w × s_a + b`，浮点 |
| GroupNorm / SiLU / GELU / softmax | 保持浮点 |

## 5. 两套实现的直接对比

| 阶段 | 原始（fp32/cuDNN） | 我们（int8 + 32×32） | 倍数 |
|---|---|---|---|
| CLIP | 0.02 s | 0.02 s | 1.0× |
| UNet × 4 | 0.47 s | 1.44 s | 3.1× |
| VAE | 0.26 s | 1.48 s | 5.7× |
| **合计** | **0.94 s** | **2.94 s** | **3.1×** |
| 有效吞吐 | 2.8 TMAC/s | 0.9 TMAC/s | |

> VAE 的差距最大（5.7×），因为它在 512² 上工作，im2col 展开的中间矩阵最庞大。

## 6. 为什么反而慢了（逐层拆解）

### 6.1 同一层卷积，两边各做什么

以 VAE 中一层典型卷积为例：H=W=512、C=128、O=128、3×3。

| 步骤 | cuDNN | 我们 |
|---|---|---|
| 布局转换 | 无（原生 NCHW） | 1 次全量转置 |
| 补边 | kernel 内部处理 | 分配 135 MB 缓冲 + 拷贝 |
| im2col | **不材料化**（隐式） | 生成 (262144 × 1152) 矩阵 = **1.21 GB** |
| 量化 | 无 | 求 max（读 1.21 GB）+ 除/取整/转 int8（再读 1.21 GB，写 0.30 GB） |
| 矩阵乘 | 融合在 kernel 内 | 独立 GEMM（读 0.30 GB，写 0.13 GB int32） |
| 反量化 | 无 | 读 0.13 GB，写 0.13 GB |
| 写回 | 直接写 134 MB | 转置 + 写 134 MB |

### 6.2 访存账本（同一层）

| 项 | 数据量 |
|---|---|
| 输入 | 134 MB |
| 补边缓冲 | 137 MB |
| im2col 矩阵 | **1.21 GB** |
| 量化输入/输出 | 1.21 GB 读 / 302 MB 写 |
| int8 矩阵 | 302 MB |
| int32 累加结果 | 134 MB |
| 输出 | 134 MB |

| 实现 | 总访存 |
|---|---|
| cuDNN | **≈ 0.27 GB**（读 0.13 + 写 0.13） |
| 我们 | **≈ 4.9 GB** |

**差约 18 倍。** 这不是 32×32 分块造成的，是「把卷积拆成 8 个独立步骤」造成的——
每一步都要把上一步的结果写回显存、再读出来。

### 6.3 int8 到底省了多少算术

| 项 | 数值 |
|---|---|
| 全链 MACs | 2596.5 GMAC |
| int8 GEMM 实测吞吐 | 3.7 TMAC/s |
| GEMM 本体耗时 | **0.70 s** |
| fp32（cuDNN）整条链耗时 | 0.94 s |

也就是说：**矩阵乘本身（0.70 s）已经接近整条 fp32 管线（0.94 s）**，
int8 的算术优势被「fp32 只算 0.94 s」这个事实压得很小。

### 6.4 全链耗时构成（热态，3.17 s）

| 环节 | 耗时 | 占比 | 属于 |
|---|---|---|---|
| 量化（amax / 缩放 / 取整 / cast） | 0.80 s | 25% | 我们额外增加的 |
| int8 矩阵乘本体 | 0.70 s | 22% | 真正的计算 |
| im2col 切片 | 0.42 s | 13% | 我们额外增加的 |
| 布局转换 + GroupNorm/SiLU/注意力/调度 | 0.91 s | 29% | 两边都要做，但我们多一次转置 |
| 补边 | 0.19 s | 6% | 我们额外增加的 |
| 反量化 + 偏置 | 0.15 s | 5% | 我们额外增加的 |

**真正在算矩阵乘的只有 0.70 s；另外 1.56 s 是「为了让矩阵乘能跑」而做的准备与收尾。**

### 6.5 其他放大因素

| 因素 | 影响 |
|---|---|
| kernel 数量 | cuDNN 每层 1 个 kernel；我们每层每块约 15 个 → VAE 全链约 1.7 万次启动 |
| Winograd | cuDNN 对 3×3 卷积减少约 2.25× 乘加；我们完全没做 |
| 逐层调度 | 282 个矩阵层，Python 侧每层都有 reshape/转置/同步开销 |
| 分块开销 | 512² 每层要切 32 块，每块独立做一次完整的量化流程 |

### 6.6 一句话总结

> **int8 省下的算术时间 < 未融合实现多花的访存与调度时间。**
> 我们省了大约 0.2 s 的矩阵乘，却付出了 2.5 s 的数据组织代价。

这是「未融合实现」的固有代价，与 32×32 矩阵单元本身无关——
同样的 int8 卷积如果写成融合 kernel（TensorRT Int8 / Q-Diffusion 的做法），
预期能到 1.0–1.5 s，与 cuDNN 同级。

## 9. 怎样才真正变快

| 措施 | 预期效果 | 说明 |
|---|---|---|
| **融合 kernel**：im2col + 量化 + IMMA + 反量化 一个 kernel 做完 | 3.17 → **1.0–1.5 s** | 关键一步，消除 4.9 GB 的中间数据落盘 |
| 权重预量化（已完成） | 已生效 | 加载时量化一次 |
| 激活量化改 per-tensor（少一遍 amax） | 省 ~0.2 s | 精度略降 |
| 避免布局转换（全程 NHWC） | 省 ~0.3 s | 需要重写周边算子 |
| 用 `torch.compile` 融合逐层算子 | 预计 1.5–2× | 不改算法，改编译器 |
| 直接跑 RTL 仿真 | 反而更慢（小时级） | 用于正确性验证，不用于出图 |

## 10. 结论

1. **替换覆盖 99.1%**：2596.5 / 2619.9 GMAC，所有卷积（101）与线性层（220）100% 走 32×32 矩阵单元。
2. **算术正确**：三种实现（IMMA / tile 快速 / tile 逐块）输出 SHA256 完全相同。
3. **画质可接受**：PSNR 22.00 dB、SSIM 0.868，损失全部来自 int8 量化。
4. **确实变慢了 3.1–3.4 倍**：0.94 s → 2.94–3.17 s，原因是未融合——
   矩阵乘本体 0.70 s，其余 2.5 s 是量化、im2col、布局转换与调度。
5. **这不是 32×32 造成的**：同样运算写成融合 kernel 可回到 1.0–1.5 s；
   而真正的硬件上限是 710 s/张。
